# 用户系统 v1：研究用例集

日期：2026-10-30。本文是研究假设和候选验收合同，不是访谈结论、上线声明或测试通过报告。目标是验证用户能否明确知道“我是谁、正在替哪个组织操作、操作会发生什么、失败后怎么办”。

## 证据与边界

- **S1**：`re8ch/user-hub` 本地干净版本 `2402df0e0b1a34a0571012d927d75ce6dd27a6d5` 的 README、`public/app.js`、`public/platform-users.js` 与 `tests/*.test.cjs`。源码存在仅说明实现线索，不证明生产可用。
- **S2**：`re8ch/identity-gitops` 基线 `a9f6f4e4e215b2a82930bdc8b7a31238f2d731a7` 的 AGENTS、README、`clusters/re8ch`。Identity 管平台约束；User Hub 和 auth gateway 的产品部署由产品仓库负责。
- **E**：已有源码/测试线索；**H**：待验证产品假设或新增验收要求。下列每项验收均为待执行标准，不能因标为 E 而记为通过。
- v1 核心范围必须通过 P0；P1 是候选体验改进；P2 延后验证。UC-14（高级组织迁移/停用）和 UC-20（购买）是条件 P0：仅在本版向用户开放该能力时纳入发布门槛；不开放时明确标记范围外并验证入口不可用，不能记为通过。严重性与出现频率分别记录，不用模拟人格的偏好投票替代用户需求。
- 仅使用合成账号和独立测试组织。Re8ch Admin 与 Re8ch 是两个组织；Admin 成员资格不构成 Re8ch 成员资格。生产充值、权限变更、删除或账户关联不属于自动模拟范围。

## 行为人格（假设）

| 编号 | 行为与目标 | 主要观察问题 |
|---|---|---|
| P-N | 首次进入的非技术用户，希望尽快使用产品 | 能否选择登录方式、识别账户、返回原任务 |
| P-R | 回访用户，在手机与桌面间切换 | 会话恢复、安全设置、失败后的任务保留 |
| P-O | 同时管理多个组织的负责人 | 是否理解当前组织、角色与操作影响 |
| P-D | 连接应用和服务的开发者 | 授权范围、服务归属与实际可用性 |
| P-S | 处理用户问题的平台支持人员 | 权限边界、操作记录与冲突处理 |

人格不包含虚构人口统计特征或伪造引语。真实访谈后允许合并、拆分或推翻这些人格。

## 前台：个人账户与授权

### UC-01 首次登录并返回原任务 · P0 · P-N

- 前置：未登录；由测试应用进入有效授权链接。
- 步骤：选择可用登录方式 → 完成验证 → 返回原请求 → 核对当前账号。
- 成功/恢复：会话属于同一 GoTrue UUID；取消登录可重新开始；回调过期明确提示从应用重启。
- 前台能力：方法说明、处理中状态、回跳；后台能力：PKCE/回调校验、会话建立与请求关联。
- 验收：每个声明可用的方法完成一次成功与一次取消路径；不丢失请求、不跳往未许可地址、不显示另一账号资料。
- 证据：E，S1 `signIn`、`finishCallback`、`oauth-native-login.test.cjs`；各提供商端到端可用性待验。

### UC-02 邮箱验证码登录与错误恢复 · P0 · P-N

- 前置：测试邮箱可收信；GoTrue 邮件 hook 已配置。
- 步骤：输入邮箱 → 获取验证码 → 先输入错误/过期码 → 再使用有效码。
- 成功/恢复：只有有效码创建会话；失败可重新请求且不丢失邮箱输入。
- 前台能力：邮箱、验证码与发送状态；后台能力：发送、过期、限流、验证。
- 验收：错误码和过期码不登录；失败按钮恢复；重复请求遵守服务端限流，提示可理解。
- 证据：E，S1 `emailOTPStart`、`emailOTPVerify`、README；限流文案与真实邮件链路为 H。

### UC-03 区分联系邮箱与登录身份 · P0 · P-R

- 前置：测试账户有 Google/Apple 身份但联系邮箱未单独验证。
- 步骤：查看身份列表 → 添加并验证联系邮箱 → 刷新资料与登录方式。
- 成功/恢复：验证前不把提供商声明的邮箱标成可用邮箱登录；验证码失败不覆盖旧联系地址。
- 前台能力：身份来源和验证状态；后台能力：独立联系地址验证、唯一性检查。
- 验收：界面与实际可用登录方式一致；拒绝验证失败的更新；账户 UUID 不变。
- 证据：E，S1 README、`renderIdentities`、`linkContact`。

### UC-04 平台账号显式关联或新建 · P0 · P-N/P-R

- 前置：合成平台 code 得到五分钟 ticket；分别准备已有和新用户。
- 步骤：选择“创建”或“关联已有” → 已有用户登录并确认 → 刷新身份列表。
- 成功/恢复：选择决定账户归属；ticket 过期后重新发起；重复消费失败且不新建第二个账户。
- 前台能力：明确的两种选择、去除 URL fragment；后台能力：单次 ticket、当前会话绑定、冲突校验。
- 验收：ticket 不留在历史或研究日志；关联保留原 UUID；未经显式选择不自动合并账户。
- 证据：E，S1 README、`finishPlatformLink`、`createPlatformAccount`、`confirmPlatformLink`。

### UC-05 应用授权允许与拒绝 · P0 · P-D/P-N

- 前置：测试客户端和有效 authorization_id；用户已登录。
- 步骤：读客户端、账号与 scopes → 分别允许和拒绝 → 回到应用。
- 成功/恢复：两种决定得到对应结果；过期请求明确重启入口；取消不授权。
- 前台能力：授权对象、范围、双选项；后台能力：请求有效性、scope 校验、安全 redirect。
- 验收：允许和拒绝都可完成；拒绝后无有效新增授权；刷新不能重复批准过期请求。
- 证据：E，S1 `renderConsent`、`decideConsent`。README 同时存在“不要求 MFA”与旧的“TOTP 后批准”描述；v1 必须对照运行契约消除冲突，不能由模拟模型决定安全政策。

### UC-06 绑定 MFA 与敏感操作二次验证 · P0 · P-R/P-O

- 前置：测试账户尚无验证器，随后完成绑定。
- 步骤：开始绑定 → 输入错误码再正确码 → 发起组织权限变更 → 完成或取消 step-up。
- 成功/恢复：只有验证成功才绑定并执行待办；取消清理待办，原变更不发生。
- 前台能力：绑定、错误提示、恢复原操作；后台能力：factor 校验、AAL 提升、敏感操作授权。
- 验收：错误码不提升权限；取消后零写入；正确码仅执行一次待办；服务端不能被绕过界面直接调用绕过。
- 证据：E，S1 `beginMfaEnrollment`、`completeMfaEnrollment`、`runOrgAction`、`cancelOrgStepUp`。

### UC-07 通行密钥登录与不可用降级 · P1 · P-R

- 前置：支持 WebAuthn 的测试设备，另备不支持/取消路径。
- 步骤：登记通行密钥 → 退出 → 使用密钥登录 → 取消一次验证。
- 成功/恢复：正确账号恢复；取消时保持未登录，可改用其他登录方法。
- 前台能力：设备提示、取消恢复；后台能力：challenge、origin 与签名校验。
- 验收：支持设备完成闭环；取消不卡住界面；不支持设备显示可行替代方法。
- 证据：E，S1 `registerPasskey`、`signInWithPasskey`；跨设备表现待验。

### UC-08 撤销其他设备会话 · P0 · P-R

- 前置：同一合成账户在两个测试浏览器登录。
- 步骤：识别当前设备 → 撤销其他设备 → 在另一浏览器执行受保护读操作。
- 成功/恢复：其他设备失去访问；当前会话保持预期状态；请求失败不谎报撤销成功。
- 前台能力：设备说明、撤销反馈；后台能力：会话撤销与 token 生命周期执行。
- 验收：按实际 token 失效契约验证其他设备拒绝访问；展示的影响时间与实测一致；记录契约与剩余窗口。
- 证据：E，S1 `renderSessions`、`signOutOtherDevices`；即时失效时间未由前台源码证明。

### UC-09 修改个人资料与头像 · P1 · P-R

- 前置：合成账户与非个人照片的图片 fixture。
- 步骤：修改名称 → 上传有效头像 → 尝试超限/无效文件 → 刷新。
- 成功/恢复：有效修改持久化；失败保留已保存资料并允许重试。
- 前台能力：字段约束、上传进度/错误；后台能力：当前用户授权、文件验证、公开头像对象管理。
- 验收：刷新保持成功结果；脚本样式文本按文字显示；界面说明头像为公开对象；无 COS 凭据进入浏览器或研究记录。
- 证据：E，S1 README、`saveProfile`、`saveAvatar`；公开性提示为 H。

## 组织管理与隔离

### UC-10 切换活动组织并识别资源归属 · P0 · P-O/P-D

- 前置：账户是两个测试组织的有效成员；每个组织有可区分 fixture。
- 步骤：查看当前组织 → 切换 → 重新读取资源 → 刷新页面。
- 成功/恢复：数据库持久化活动上下文；切换失败保留原上下文并提示。
- 前台能力：组织名称、活动标记、成功反馈；后台能力：`select_active_organization` 成员校验与上下文解析。
- 验收：后续请求与刷新均只使用选中组织；不能通过自填 header 获得其他组织权限；旧组织资料不残留为当前数据。
- 证据：E，S1 `renderOrganizationCenter`、`selectActiveOrganization`、`active-organization.test.cjs`；跨页面旧缓存清除待验。

### UC-11 Admin 与应用组织权限严格分离 · P0 · P-S/P-O

- 前置：两个合成账户，分别只有 Admin 成员资格和应用组织成员资格。
- 步骤：分别登录 → 查看可选组织和目录 → 尝试越权读取/变更另一组织 fixture。
- 成功/恢复：非授权请求被服务端拒绝；提示缺少对应组织成员资格，提供正确加入流程。
- 前台能力：组织上下文和无权限解释；后台能力：同组织有效 membership 校验、授权边界。
- 验收：所有交叉访问拒绝且零副作用；不自动激活另一组织成员；记录拒绝证据但不记录敏感 payload。
- 证据：E，S1 README 的 membership 权威与目录作用域；H，完整负向验收矩阵。

### UC-12 创建与重命名组织 · P1 · P-O

- 前置：有创建权限的合成账户；有效 AAL；无真实企业数据。
- 步骤：创建测试组织 → 重名/非法 ref 再试 → 重命名 → 刷新目录。
- 成功/恢复：有效创建仅一次；无权限或冲突反馈明确，保留可修正字段。
- 前台能力：表单、父组织、目录刷新；后台能力：唯一 ref、权限、审计。
- 验收：名称和父子关系回读一致；重复提交不会产生重复组织；普通成员不能通过直接请求创建。
- 证据：E，S1 `createOrganization`、`renameOrganization`；重复提交控制需验证。

### UC-13 添加成员、改角色与移除 · P0 · P-O

- 前置：测试组织负责人、成员及无权账号；预设角色矩阵。
- 步骤：添加成员 → 改角色 → 成员重读能力 → 移除 → 再访问。
- 成功/恢复：服务端按当前 membership 授权；非法提升/冲突拒绝并可刷新。
- 前台能力：目标账号、组织、角色和影响确认；后台能力：角色约束、权限失效、审计。
- 验收：每个角色允许/拒绝矩阵与实际一致；移除后无法继续受保护操作；无权用户不能自我提权。
- 证据：E，S1 `saveMember`、`removeMember`、`runOrgAction`；后端矩阵待端到端验证。

### UC-14 组织迁移与停用影响可理解 · 条件 P0 · P-O/P-S

- 前置：隔离测试组织树；准备 root Admin 与独立 Personal fixture。
- 步骤：预览拟迁移对象 → 移动合法组织 → 尝试移动受保护对象 → 取消及确认停用。
- 成功/恢复：合法变更回读一致；受保护对象拒绝；取消停用没有写入。
- 前台能力：目标、父组织和直属成员影响提示；后台能力：层级约束、root Admin 保护、成员失效。
- 验收：不产生组织环；root Admin 不能被移动；独立 Personal 不被隐式吸收；确认前明确权限失效范围。
- 证据：E，S1 README、`moveOrganization`、`archiveOrganization`；影响预览深度为 H。

## 隐私与平台后台

### UC-15 下载自己的身份快照 · P0 · P-R

- 前置：有资料、设备及申请记录的合成账户。
- 步骤：下载 → 查看 JSON 范围 → 撤销会话后再试。
- 成功/恢复：文件只含当前用户身份数据；会话失败显示错误并恢复按钮。
- 前台能力：下载与范围说明；后台能力：仅本人读取、无凭据导出。
- 验收：包含范围与文案一致；不含产品数据/认证凭据/其他用户数据；失败不下载伪成功文件。
- 证据：E，S1 `downloadIdentityExport`、`privacy-requests.test.cjs`。

### UC-16 提交、取消和跟踪账户申请 · P0 · P-R

- 前置：合成账户；导出与删除分别运行。
- 步骤：提交申请 → 查看 pending → 取消 → 再提交 → 后台进入处理 → 查看历史。
- 成功/恢复：提交不是立即删除；pending 可取消；处理中不再显示取消；冲突需刷新。
- 前台能力：后果确认、状态、说明和时间线；后台能力：状态机、version 校验、审计。
- 验收：重复/冲突不产生矛盾终态；无自动重试写入；用户能区分身份快照、完整导出申请与注销申请。
- 证据：E，S1 `requestAccountAction`、`renderAccountRequests`、隐私测试。

### UC-17 后台履约、拒绝与并发冲突 · P0 · P-S

- 前置：测试管理员；一条 pending 申请；两个并发管理页面。
- 步骤：开始处理 → 尝试无凭证完成 → 提供合成履约引用 → 完成；另一路提交旧版本。
- 成功/恢复：必须先处理再完成；拒绝有用户可见解释；旧版本失败且要求刷新。
- 前台能力：管理员状态选项、说明与凭证字段；后台能力：状态/版本校验、证据隔离、审计。
- 验收：pending 不能直接完成；无证据不能完成；用户看不到管理员凭证；旧版本只发起一次写请求；“完成”须有实际履约证据。
- 证据：E，S1 `renderAdminAccountRequests`、隐私测试。该流程记录履约，不执行跨产品物理删除。

### UC-18 平台用户目录与受控维护 · P0 · P-S

- 前置：测试平台管理员和普通用户；仅使用合成用户。
- 步骤：分页查找 → 查看详情 → 修改测试字段 → 普通用户尝试相同端点。
- 成功/恢复：管理员操作成功可回读；未登录/无权请求拒绝；失败不自动重试写入。
- 前台能力：分页、明确目标、错误与受控表单；后台能力：管理员授权、字段验证、审计。
- 验收：普通用户无法读写目录；恶意显示名按文字渲染；拒绝写入没有副作用；任何删除测试另用可丢弃 fixture。
- 证据：E，S1 `public/platform-users.js`、`platform-users.test.cjs`。

## 用量、服务与通用体验

### UC-19 区分资源用量、扣款和购买记录 · P0 · P-O/P-D

- 前置：测试组织有不同时间的用量、Credits 扣减与订单 fixture。
- 步骤：打开账单 → 分别查看三类记录 → 空数据和读取失败各运行一次。
- 成功/恢复：计量、实际 Credits 扣减、购买记录分别解释；读取失败不显示“零用量”假结论。
- 前台能力：单位、时间范围、组织归属、空/错状态；后台能力：只读视图与租户过滤、分页。
- 验收：各展示值能追溯到对应 fixture；不将用量自动解释成费用；跨组织读取失败；错误和空状态可区分。
- 证据：E，S1 README、`loadBilling`、`loadSpend`、`loadPurchases`；理解程度为 H。

### UC-20 积分购买的不确定状态恢复 · 条件 P0 · P-R

- 前置：支付沙箱或本地合成订单；禁止真实扣费。
- 步骤：创建订单 → 模拟响应丢失 → 刷新恢复 → 分别模拟 paid/closed/expired。
- 成功/恢复：同一结算重用幂等键；未确认支付显示未知并查同一订单；过期可重新开始。
- 前台能力：本地二维码、状态、订单恢复；后台能力：幂等订单、可信支付确认、入账一致性。
- 验收：重试不产生重复有效订单/重复入账；未知不显示成功；二维码不发给第三方图片服务；成功提示与钱包实际入账一致。
- 证据：E，S1 `buyCommerceCredits`、`watchCommerceOrder`、README；端到端支付一致性必须沙箱验证。

### UC-21 服务可用性与连接引导 · P1 · P-D

- 前置：当前组织分别有 Ready、不可用、无授权三种服务 fixture。
- 步骤：看已关联服务 → 选择能力 → 不可用时寻找下一步。
- 成功/恢复：区分已授权与实际 Ready；不可用说明重试/申请途径。
- 前台能力：归属、能力解释、可用状态；后台能力：当前租户 grants、服务健康与连接资料边界。
- 验收：不把 grant 当作 Ready；不展示其他组织连接信息或凭据；无能力时有明确空状态。
- 证据：E，S1 `loadServices`、`loadTenantCapabilities`；Ready 语义与补救入口为 H。

### UC-22 会话过期、网络失败与重新进入 · P0 · P-R/P-O

- 前置：任一只读页面及一个合成写入表单；可控 401/403/503/超时。
- 步骤：过期读 → 重新登录；写入时模拟响应丢失 → 查询实际状态再决定重试。
- 成功/恢复：不泄漏旧账号内容；读重试有入口；不盲目重放非幂等写入。
- 前台能力：一致错误分类、重新登录/刷新、按钮解锁；后台能力：会话校验、请求状态或幂等约束。
- 验收：四类故障逐项有可行动反馈；每项写入至多产生一个预期结果；切账号后无前账号数据残留。
- 证据：E，S1 `validSession`、隐私 HTTP client 与平台用户测试；跨模块统一体验为 H。

### UC-23 手机、键盘与语言切换 · P1 · P-N/P-R

- 前置：窄屏与桌面视口；键盘；中文/英文测试内容。
- 步骤：登录 → 切组织 → 查看账单 → 仅键盘完成隐私申请；切换语言后刷新。
- 成功/恢复：关键按钮可见、焦点可追踪，错误与状态可被感知；语言切换不丢失会话。
- 前台能力：响应布局、标签、焦点、状态区和本地化；后台能力：不依赖显示语言进行授权。
- 验收：所有 P0 入口在窄屏可到达且无关键遮挡；Tab 可到达操作并可取消；中文/英文不混淆相同状态；不得用机器翻译存在推断质量合格。
- 证据：E，S1 `applyLocale`、`translateStatic`、HTML labels/status；可访问性与翻译质量为 H，需实际浏览器验证。

## 执行记录要求

每次执行保存：用例 ID、persona ID、源 revision、环境、合成 fixture ID、角色/组织、实际步骤、预期/观察差异、脱敏截图或 DOM 引用、服务端只读回查证据、通过/失败/阻塞、发现 ID。只记录不含凭据的引用；不把 bearer、ticket、邮件/手机或支付二维码写进 GitHub。

LiteLLM 模拟产生的是候选摩擦点。只有真实界面操作与回查证据可标记“观察到”；只有按验收合同检查才可标记“通过”。没有真实用户参与时，满意度、转化率、人格比例均记为未知。

## v1 研究决策队列

1. **授权 MFA 契约冲突**：明确普通授权与敏感设置的差异，修订 User Hub 文档并补真实流程证据（UC-05/06）。
2. **组织上下文可见性**：验证切换后服务与账单不会呈现旧组织数据，确认 Admin/App 边界（UC-10/11/19）。
3. **失败后的可信状态**：统一“未执行/已执行/未知/需刷新”，优先写入与支付不确定状态（UC-16/17/20/22）。
4. **权限管理可理解性**：验证用户能预判改角色、移除和停用的影响；先验收服务端拒绝矩阵（UC-13/14）。
5. **范围与承诺一致**：身份快照不等于全部数据；记录完成不等于自动删除；grant 不等于可用（UC-15/17/21）。

以上是源码导出的研究方向，不是已证实的用户痛点。新增产品能力应在各产品仓库建实施工作项；本仓库仅保存研究合同和平台期望边界。
